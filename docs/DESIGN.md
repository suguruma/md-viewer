# 設計文書

## 1. 技術スタック比較(3案)

| 観点 | 案A: Node + Express + unified SSR + 素のJS | 案B: Vite + React SPA + Node API | 案C: Tauri デスクトップアプリ |
| --- | --- | --- | --- |
| 起動の手軽さ | ◎ `npm start` のみ、ビルド工程なし | △ ビルドまたは dev サーバー2層 | × Rust ツールチェーン+ビルド必須 |
| プラグイン拡張性 | ◎ サーバー側パイプラインに直挿し | ○ 可能だがバンドルに巻き込む必要 | ○ 同左 |
| 実装・保守コスト | ◎ 依存少、全コードが可読な素のJS | △ React+ビルド設定の維持 | × 最重量 |
| UIリッチさ | ○ 個人用途には十分 | ◎ | ◎ |
| 配布 | ○ フォルダごとコピーで動く | ○ | ◎ 単一exe |
| 主リスク | UIが素朴になりがち | 「1コマンド起動」要件を汚す | 個人メモビューアーに過剰 |

**採用: 案A。** 決め手は (1) ビルド無しで1コマンド起動、(2) remark/rehype プラグインを Node 側で `processor.use()` するだけの最短拡張経路、(3) 数百ファイル・個人利用というスケールに対する適正コスト。

### 却下した代替案

| 代替案 | 却下理由 |
| --- | --- |
| 案B(React SPA) | ビルド層が起動要件と保守性を悪化。UIの複雑さが要件にない |
| 案C(Tauri/Electron) | 配布は良いが開発・更新の重量が個人ツールに見合わない |
| クライアントサイドレンダリング(unifiedをバンドル) | esbuild等のビルド工程が必須になり、プラグイン追加=再バンドルで拡張性が悪化 |
| 既存OSS利用(docsify / mdBook / VSCodeプレビュー / Obsidian) | mdBookはSUMMARY.md必須のビルド型、docsifyはツリー自動生成が弱い。単一ファイルモード+任意フォルダCLI+remark互換プラグイン+横断検索+ライブリロードの**組み合わせ**を満たすものがなく、自作の拡張基盤を持つこと自体が本タスクの目的 |
| markdown-it / marked | プラグイン資産とAST変換の柔軟性で unified(remark/rehype)が要件に合致 |
| 検索のインデックス化(lunr等) | 500ファイル実測75msの逐次スキャンで十分。索引の鮮度管理コストが割に合わない |

## 2. アーキテクチャ

```
ブラウザ (public/: 素のJS + CSS)
  │  GET /api/tree /api/doc /api/search /raw/*      WebSocket /ws
  ▼                                                    ▲
Express (server/index.js) ── chokidar 監視 (watch.js) ─┘
  │
  ├─ render.js: unified パイプライン + mtimeキャッシュ(50件)
  ├─ tree.js / search.js: フォルダ走査・横断検索
  └─ config.js: md-viewer.config.mjs 読み込み(ユーザープラグイン)
```

- **サーバーサイドレンダリング**: Markdown→HTML は Node 側。クライアントは受け取ったHTMLの後処理(mermaid描画・目次・検索)のみ
- **mermaid だけクライアント描画**: mermaid は DOM 必須のため。サーバーは ```mermaid ブロックを `<div class="mermaid-block"><pre>ソース</pre></div>` に変換して渡す(JS無効時はソース表示のフォールバックになる)
- **単一ファイルモード**: ルート=親フォルダとして相対画像を解決しつつ、UI はサイドバー非表示

### レンダリングパイプライン(順序が重要)

```
remark-parse → remark-frontmatter → remark-gfm → remark-math
  → [ユーザーremarkプラグイン] → remark-rehype(allowDangerousHtml)
  → rehype-raw → rehype-slug → rehype-katex
  → mermaidブロック分離(shikiに食わせない)
  → 未知言語のクラス除去(shiki例外防止)
  → @shikijs/rehype(ライト/ダーク両テーマをCSS変数で焼き込み)
  → 相対リンク書換(画像→/raw、.md→#/ハッシュ遷移)
  → 見出し収集(アウトラインAPI用)
  → [ユーザーrehypeプラグイン] → rehype-stringify
```

### API

| エンドポイント | 内容 |
| --- | --- |
| `GET /api/config` | モード(dir/file)、ルート名、初期ファイル |
| `GET /api/tree` | .md のツリー(空フォルダは枝刈り) |
| `GET /api/doc?path=` | `{html, headings[], plain, mtimeMs}` |
| `GET /api/search?q=` | 横断検索。ファイルごとの行スニペット(上限200件) |
| `GET /raw/<path>` | 画像等の生ファイル(ルート配下限定) |
| `WS /ws` | `doc-changed` / `tree-changed` を配信 |

## 3. 主要な設計判断と理由

| 判断 | 理由 |
| --- | --- |
| shiki(dual theme, `defaultColor:false`) | ライト/ダーク両テーマの色をCSS変数として1回のレンダリングで埋め込み、テーマ切替時に再レンダリング不要(mermaidのみ再描画) |
| テーマ切替時は保持済みHTMLから本文を再構築 | mermaidはテーマをSVGに焼き込むため。`state.payload` から innerHTML を張り直して再描画する |
| mtime+size キャッシュ(最大50件) | ライブリロードや再訪時の再レンダリングを2ms程度に。監視イベントでも明示的に無効化 |
| 起動時ウォームアップ | shiki初期化は実測4.5秒。起動直後に裏でダミーレンダリングし、初回表示を223msに短縮 |
| 2MB超はプレーン表示 | ハイライト・数式処理の時間暴走を防ぐ。通知バナー付き |
| HTMLサニタイズなし + 127.0.0.1 バインド + Host/Origin 検証 | 対象は自分のローカルファイル。XSS脅威モデルが成立しない一方、rehype-raw による生HTML表現力を優先。不信文書用に rehype-sanitize を config で追加可能。ループバック限定でも Web ページ経由(DNS リバインディング)で到達されるため、Host/Origin の検証と、他のオリジンからの読み込み・埋め込みを止める応答ヘッダーを併用する(§11) |
| パストラバーサル防御 | `path.resolve` 後にルートプレフィックス検証(`/api/doc`・`/raw` 共通)。実測: `../../package.json` → 400/403 |
| 検索は索引なしの逐次スキャン | 500ファイル実測75ms。複雑さを増やす根拠がない |
| ツリーは展開時に子を遅延描画 | 数百〜数千ノードでも初期描画を軽く保つ |
| CDN不使用(katex/mermaidをnode_modulesから配信) | オフラインで完全動作 |
| Express採用(素のhttpでなく) | static配信・sendFile・Content-Type処理の実績を4ルートのために自作しない |

## 6. Windows配布(exe化)の設計判断(追記, 2026-07-11)

初回納品後、Windows向けのポータブル版・インストーラー版の要望を受けて追加した部分。

### 6.1 exe化方式の比較

| 方式 | 概要 | 判定 |
| --- | --- | --- |
| **Node SEA(採用)** | Node公式のSingle Executable Applications。node.exeに小さなブートストラップblobをpostjectで注入 | ◎ 公式機能、node_modulesは通常ファイルのまま隣に置けるため資産埋め込み不要 |
| pkg / nexe | 旧来のJSバンドル型exe化ツール | △ vercel/pkgは非推奨化。shikiの動的import(言語文法の遅延読み込み)と相性が悪い |
| Electron/Tauri再検討 | GUIシェルで包む | × 既にブラウザ+HTTPサーバー構成が動いており、GUIシェル化は要件にない過剰投資 |

**設計**: `mdv.exe`(SEA)は最小のブートストラップのみを内蔵し、`import()` で隣接する `app/bin/mdv.js` を動的読み込みする。サーバー本体・クライアント資産・`node_modules` はexeに埋め込まず隣接フォルダに通常ファイルとして配置する。理由: shikiの言語文法・mermaid資産などをSEAのアセット埋め込みAPI(`sea.getAsset()`)向けに全面書き換えするコストとリスクが、通常ファイル配置のシンプルさに見合わない。

**実機検証で判明した重要事実**: SEA実行時の `process.argv` は `[execPath, execPath, ...userArgs]`(先頭が重複)であり、通常の `node script.js args...`(`[node, script, ...args]`)と同じ `slice(2)` 位置にユーザー引数が並ぶ。この事実により `bin/mdv.js` の `util.parseArgs` 呼び出しは**無改造**でexe版・ソース版の両方に対応できた(検証: `build/sea-test` プロトタイプで `test.exe foo bar baz` の実際の argv を出力して確認)。

### 6.2 ポータブル版のnode_modules軽量化

`node_modules` の実測143.7MBのうち、`mermaid` パッケージ単体が79.7MB(依存の `@mermaid-js/parser` 等を含めると約100MB)を占めていた。調査の結果、mermaidはサーバーコードから一度も `require`/`import` されておらず、`express.static()` で `node_modules/mermaid/dist` を配信しているだけと判明(`server/index.js` 参照)。実際にクライアントが読み込むのは `mermaid.min.js` 1ファイル(3.4MB)のみで、`.map` ファイルや非min版、ESM分割版は不要。

**対処**: ポータブル/インストーラー版のビルド時のみ、`mermaid.min.js` 以外のmermaid関連ファイル一式(`@mermaid-js`, `cytoscape`, `cytoscape-fcose`, `d3`, `dompurify`, `es-toolkit`)を除外し、必要な1ファイルだけを配置。`npm ls --all` でこれらのパッケージがmermaid以外から参照されていないことを確認済み。結果: dist/portable 121.7MB(zip 43.5MB)。開発用の `node_modules` 自体は変更していない(ビルドスクリプトのコピー処理のみで除外)。

### 6.3 インストーラーの権限モデル

Inno Setupの `PrivilegesRequired=lowest` を採用し、管理者権限なしで `%LOCALAPPDATA%\Programs\MDViewer` にユーザー単位インストールする設計とした。理由: 個人の閲覧ツールに管理者権限を要求するのは過剰であり、UAC昇格プロンプトはインストール障壁になる。PATH追加はデフォルトでは行わず、タスク選択(既定オフ)にした上で、アンインストール時に追加分だけを正確に削除するPascalScriptを実装(単純な文字列連結ではなく `Pos` で重複チェック・部分削除)。

### 6.4 署名について

コード署名証明書は取得していない(個人の無料配布ツールに対して費用対効果が見合わない判断)。`signtool remove /s` で元のnode.exeの署名を明示的に除去してから `postject` で注入することで、「署名が壊れている」という不整合な状態を避けた(除去しない場合、postjectが "signature seems corrupted" 警告を出すことをプロトタイプ検証で確認済み)。Windows SmartScreenの初回警告は避けられないため、README/インストーラー双方に対処方法(詳細情報→実行)を明記した。

## 7. フォルダ切替・アクセシビリティ・メタデータ機能の設計判断(追記, 2026-07-11)

### 7.1 フォルダ選択に `window.prompt()` を採用した理由

ブラウザの File System Access API(`showDirectoryPicker()`)はサンドボックス化されたハンドルを返すのみで、実OSの絶対パス文字列を取得できない。本アプリのサーバーはNodeの `fs` で実パスを直接読むアーキテクチャのため、ハンドルベースのAPIとは根本的に相性が悪い(ハンドル→絶対パスの変換手段がブラウザ標準には存在しない)。よって絶対パスをテキストで直接受け取れる `prompt()` を採用した。ネイティブのフォルダ選択ダイアログ相当のUXは失うが、要件(サーバー側で実パスを扱う)を満たす現実的な選択肢はこれのみだった。

### 7.2 フォルダ切替時のキャッシュ・監視の扱い

`POST /api/change-dir` はレンダリングキャッシュを**全消去**し、chokidarの監視インスタンスを**破棄して作り直す**方式にした。相対パスキー(例: `index.md`)は新旧ルートで意味が変わるため、部分的な無効化では新ルートの同名ファイルが誤って旧ルートのキャッシュを返すリスクがある。監視インスタンスも同様に、生きたままターゲットだけ変える chokidar API は存在しないため、破棄→再生成が唯一の正しい方法。実装は `restartWatcher()` に集約し、初回起動時のwatcher生成とフォルダ切替時のwatcher再生成で同じコールバック(`handleDocChanged`/`handleTreeChanged`)を共有する。

### 7.3 ツリーのキーボード操作は roving tabindex パターン

各行に個別の `tabindex="0"` を与えず、常に1行だけが `tabindex="0"` を持ち、他は `-1`(roving tabindex、WAI-ARIA Authoring Practices の tree パターンに準拠)。理由: ツリー全体を1回の `Tab` で通過できるようにするため(行数分Tabを押させるのは数百ファイル規模で破綻する)。矢印キーでのフォーカス移動時に `setRovingTabIndex()` で「次にTabで入ってくる位置」を更新する。フォルダは遅延DOM生成(初回展開まで子要素が存在しない)のため、「表示中の行」は `offsetParent !== null` で都度再計算しており、事前に構造をインデックス化していない(数百ファイル規模でも実用速度である前提、実装複雑化を避けた)。

### 7.4 フロントマターの解析ライブラリに `yaml` を採用

`remark-frontmatter` は生YAML文字列をAST上に保持するだけで構造化はしない。パース専用に `js-yaml` ではなく `yaml`(eemeli/yaml)を選定した理由: 依存が0でモダン、YAML 1.2準拠、メンテナンスが活発。パース結果はremarkプラグイン内でASTノードから直接除去し、`file.data.frontmatter` に格納する(remark-rehypeの「未知ノードは無視される」という暗黙の挙動に依存しない明示的な実装とした)。

### 7.5 絵文字はオプトインではなく既定で有効化

要求は「デフォルトでオンにするか、UIトグルを用意するか」の二択だったが、デフォルトオンを選んだ。理由: UIトグルはサーバー側の再レンダリング設定を実行時に切り替える仕組み(設定の永続化、キャッシュ無効化、UIの追加)を必要とし、GFM相当の期待値(GitHub上で `:smile:` が絵文字になるのと同じ体験)に対して実装コストが見合わない。`remark-emoji` は既存のプラグイン注入ポイント(`config.remarkPlugins`)ではなく、GFM/数式と同格の**組み込み機能**としてパイプラインに直接追加した。

### 7.6 フォルダ切替がもたらすセキュリティ境界の変化

`POST /api/change-dir` は許可リストなしで「存在するディレクトリか」のみを検証する。これにより、`--host 0.0.0.0` で起動された場合の攻撃対象範囲が、起動時に固定されたルート配下から「OSユーザーが読み取れる任意のディレクトリ」に拡大する。既存の脅威モデル(認証なし・ループバック前提)そのものは変えず、この拡大をREADME/FEATURESの両方に明記する対処とした。追加の許可リストや確認フローは、個人用ツールの手軽さを損なうため見送った。(追記 2026-10-19: ループバック限定でも Web ページ経由で到達されうることが分かったため、Host / Origin の検証を追加した。§11)

## 8. 前回フォルダの自動復元(追記, 2026-07-11)

「ダブルクリック起動のたびにフォルダを選び直すのが面倒」という要望への対処。サーバー側に永続設定ファイルを持たせる案(起動オプションで最後に開いたパスを記憶)ではなく、**クライアント側の `localStorage`** に「最後に開いたルート」を保存し、起動時にハッシュ未指定であれば自動的に `changeDir()` を呼び直す設計にした。

理由:
- サーバーはCLI起動のたびに新プロセスとして立ち上がり、既存の設計上どこにも永続状態を持たない。設定ファイルの読み書き機構を新設するより、既に実装済みの `POST /api/change-dir` をクライアントから呼ぶだけで完結する方が変更が小さい。
- ポータブル版・インストーラー版とも、ショートカット/exeへの引数は固定(同梱サンプルを指す)のままで済む。引数を動的に書き換える仕組みは不要。
- 復元は `silent: true` で失敗を握りつぶし、フォルダが移動・削除されていた場合は該当エントリを消去して次回以降は既定のサンプル表示にフォールバックする(壊れた記憶を無限に再試行しない)。
- URLにフラグメント(`#/path.md`)が既にある場合は自動復元をスキップする。ブックマークや履歴からの再訪問時に、記憶されたフォルダへ無断で切り替えてしまうことを避けるため。

## 9. マインドマップ・双方向編集機能の設計判断(追記, 2026-07-14)

「プレビュー↔エディタの双方向連携」「マインドマップ表示」の要望への対処。着手前に、現状把握(パーサーは既にremark/unified、UIフレームワークなし=素のJS、そして最大の論点として**エディタ画面が存在しない閲覧専用アプリ**であること)をユーザーに提示し、書き込み機能を追加する設計判断そのものについて承認を得た上で実装した。

### 9.1 パーサー移行は不要と判断した経緯

要求文は「現在のパーサーからの移行(例: remark/unifiedへ)が必要なら許可を求める」という条件付きだったが、本アプリは既に `unified`/`remark-parse`/`remark-rehype` で構築済みだったため、この条件自体が発生しなかった。位置情報(ソースマッピング)についても、`remark-parse` は既定でASTノードに `position.start.offset`/`position.end.offset` を保持しており、追加のプラグインやパーサー変更なしに利用できることを実測で確認した(下記9.3参照)。これにより「サーバーは最終HTML文字列のみを返し、クライアントに生Markdownや位置情報は一切渡さない」という既存アーキテクチャに、位置情報を**属性として**運ぶ薄い層を足すだけで要件を満たせた。

### 9.2 マインドマップ: 俯瞰モード方式 + markmap-lib/markmap-view

「ドキュメント全体をマインドマップとして俯瞰するモード」と「特定記法(コードブロック等)をマインドマップとして描画する仕組み」の二択のうち、前者を採用した。理由: 要求文が「Markdownの階層構造(見出しやリスト)を解釈し」と述べており、これは対象ドキュメント自身の構造を指すと読むのが自然で、後者(Mermaidと同型の専用フェンス記法)は「別途書いたミニマインドマップをドキュメント内に埋め込む」用途に近く、要求の趣旨とずれる。

実装は、Mermaid同様に `markmap-lib`(markdown-it独自パーサーでMarkdown→ツリー変換)と `markmap-view`(d3で描画)をkatex/mermaidと同じ「node_modulesからvendor配信、CDN不使用」方式で追加した。ビルド済みブラウザ向けバンドル(`markmap-lib/dist/browser/index.iife.js`、`markmap-view/dist/browser/index.js`)はそれぞれ内部に markdown-it/highlight.js/prismjs/katex や d3 依存のロジックを同梱しているが、`markmap-view` 側だけは実行時にグローバル `d3` を要求するため、`d3` パッケージも新たにvendor配信対象に追加した(`markmap-lib` 側は `window.katex` を参照するが、これは任意機能でundefinedでも例外にならないため無視してよいことを確認済み)。

**マインドマップ用の生Markdown取得に新規APIは不要だった**: `GET /raw/<path>` は元々「ルート配下の任意ファイルを配信する」実装(画像用)であり、`.md` 拡張子を除外していなかったため、そのままクライアントから生Markdown取得に転用できた。レンダリング済みHTMLより機微性の低い情報(生テキスト)を同じ読み取り専用ルートで返すだけであり、新たな脅威モデル変化はない。

### 9.3 チェックボックス・テキスト装飾の位置特定: hPropertiesでAST位置情報をHTML属性に橋渡し

remarkのAST(mdast)ノードは `data.hProperties` に値を設定すると、`remark-rehype` がそれを対応するHTML要素の属性としてそのまま出力する(unified/remark-rehypeの標準的な拡張ポイントで、rehype側の変更は不要)。これを利用し:

- `remarkTagTaskCheckboxes`: チェック付き `listItem` ノードの `position.start.offset` から数文字分の窓を取り、`/\[[ xX]\]/` で `[ ]`/`[x]` マーカーの正確なオフセットを特定して `data-task-start`/`data-task-end` を `<li>` に付与する。
- `remarkTagBlockPositions`: `paragraph`/`heading` ノードそれぞれに `position.start.offset`/`position.end.offset` をそのまま `data-src-start`/`data-src-end` として付与する。

いずれも実際にレンダラーへ渡した後のHTML出力を確認するテストスクリプトで、日本語テキスト・ネストしたチェックリスト・CRLF改行の3パターンについてオフセットが原文と正確に一致することを実測で検証してから本実装に進んだ。

### 9.4 書き込みAPIの信頼モデル: 「どこに」はクライアントから、「何を書くか」は常にサーバーが決める

このアプリで初めてファイル書き込み機能(`POST /api/doc/toggle-task`、`POST /api/doc/wrap-selection`)を追加するにあたり、クライアントから任意の置換文字列を受け取らない設計にした。

- チェックボックス: クライアントは `{path, start, end, wasChecked}` を送るのみ。サーバーはファイルを独立に再読込し、該当範囲が `wasChecked` の状態と一致するかを検証したうえで、置換後の文字列(`[ ]`⇔`[x]`)自体をサーバー側で決定する。
- テキスト装飾: クライアントは `{path, start, end, expectedText, style}` を送る。`style` は `"strike"`/`"underline"` のいずれかのみ受け付け、実際に書き込む `before`/`after`(`~~`/`~~`、`<u>`/`</u>`)はサーバー内の固定テーブルから引く。`expectedText` が実ファイルの該当範囲と一字一句完全一致しない限り書き込まない(`409`)。

この設計により、リクエストボディの値がそのままファイルに書き込まれる経路が存在しない。認証なし・ループバック前提という既存の脅威モデルの上に書き込み機能を足す以上、「任意のバイト列を書ける」原始的なAPIにしないことが最低限の防御ラインだと判断した。

### 9.5 テキスト装飾の範囲特定で発覚したCRLFバグと、その修正方針

当初の実装は「レンダリング後のDOMテキストで選択開始位置までの文字数を数え、ブロック先頭の原文オフセットに加算する」という単純な方式だった。ブラウザでの実地検証で、CRLF改行を含むファイル(このアプリのサンプルデータも含め、Windows環境では一般的)で複数行にまたがる段落を選択すると、書き込み位置が1文字ずれる不具合を発見した。原因は、原文の改行が `\r\n`(2文字)であるのに対し、remark-rehypeがsoftbreakをレンダリングする際は `\n`(1文字)としてHTML化するため、DOM側の文字数カウントと原文の文字数が行またぎのたびにズレていくこと。

**修正**: 文字数の加算方式をやめ、「該当ブロックの生テキスト(`GET /raw/<path>` で取得)の中から、選択文字列(`selection.toString()`)を直接検索する」方式に変更した。同じ文字列がブロック内に複数回現れる場合のみ、DOM側のおおよその文字数を「どの出現を採用するか」の判定材料として補助的に使う。この方式は改行コードの差異だけでなく、選択範囲より前に強調・リンク・インラインコード・数式(KaTeXが埋め込む隠しアクセシビリティテキストを含む)があるためレンダリング後テキストが原文より短い一般のケースも自然に吸収する(検証: `` `code`、**強調**、$E=mc^2$ も本文中に書けます `` という段落の末尾を選択して打ち消し線を適用し、正しい位置に反映されることを確認)。「単一ブロック内の選択のみサポート」という当初の限定は保ったまま、そのブロック内での位置特定精度を大きく引き上げる結果になった。

### 9.6 マインドマップのノード直接編集を見送った理由(ステップ5)

markmapはMarkdown→図の片方向可視化ライブラリであり、描画済みノードを編集した際に元のMarkdown上の位置へ逆マッピングする仕組みを標準では持たない。これを自前で構築する場合、9.3で実装した段落/見出し単位の位置特定とは別に、markmap独自のツリー構造・折りたたみ状態・ノードごとのHTML断片をすべて原文位置へ対応付ける層が新たに必要になり、9.5で発覚したような食い違いのリスクがマインドマップ側でも同様に(あるいはそれ以上に)発生する。実装コストとリスクに対して得られる価値が見合わないと判断し、ユーザー承認のもとで簡易版の代替(ノードクリックで通常プレビューの該当箇所へジャンプ。見出しは完全一致、それ以外は既存のページ内検索機構を再利用)に置き換えた。

### 9.7 ポータブル版ビルドのvendor除外リスト更新

`build/build-portable.mjs` の `EXCLUDE_DIRS` には元々 `'d3'` が含まれていた(mermaidの依存として)。今回d3を新たに直接vendor配信する必要が生じたため、この既存の除外設定を放置すると**ポータブル版でマインドマップ機能が壊れる**(`d3.min.js` が同梱されず404になる)ことに気づき、修正した: `'d3'` 自体は除外対象から外し、代わりにd3の実行時未使用サブパッケージ(`d3-array`〜`d3-zoom`、mermaid依存の`d3-sankey`含む)を個別に除外リストへ追加。同様にmarkmap-lib/markmap-view専用の巨大な依存(`markdown-it`系、`highlight.js`、`prismjs`、`markmap-common`等、いずれも `npm ls` で他から参照されないことを確認済み)も除外し、実配信するファイル(`d3/dist`、`markmap-view/dist/browser`、`markmap-lib/dist/browser`)だけをmermaidと同じパターンで個別コピーする方式にした。

## 10. ポップアウトプレビュー(別ウィンドウ表示)の設計判断(追記, 2026-07-14)

「プレビューを別ウィンドウ/タブで開き、マルチディスプレイ環境でリアルタイム同期する」という要望への対処。

### 10.1 「エディタのテキスト変更を同期」という前提の読み替え

要求文は「メインウィンドウ(エディタ側)とサブウィンドウ(プレビュー側)」「エディタのテキスト変更が即座に反映」という表現で、双方向編集機能(§9)と同様、**このアプリにエディタ画面が存在しない**という前提と食い違っていた。実装着手前にこれをユーザーに提示し、「メインウィンドウが今表示しているファイル・テーマ・マインドマップ表示」という**表示状態**を同期する形に読み替えて進めることを明確にした(既存の「編集は外部エディタ、保存されたらchokidar+WebSocketで反映」という設計は変えていない)。

この読み替えにより、実は要求の一部は**既存の仕組みで既に満たされている**ことに気づいた: 同じファイルを2つの通常タブで開いていれば、外部エディタでの保存は今まで通り両方のタブに(各タブが独立に持つ `/ws` 接続経由で)リアルタイムに反映される。今回新規に必要だったのは、(1) プレビュー専用のシンプルなレイアウト、(2) 「どのファイルを見ているか」というナビゲーション状態の同期(素のタブでは各タブが別々のハッシュを持ってしまうため)、(3) ポップアウトの開閉・ウィンドウ管理UI、の3点のみだった。

### 10.2 別ビルドではなく `?popout=1` によるレイアウト分岐

専用のプレビューHTML/JSを新設する案もあったが、mermaid描画・KaTeX・マインドマップ・ライブリロードなど本文表示に関わるロジックがすべて `app.js` に集約されており、これを複製すると保守時に2箇所を同期し続ける負担が生じる。代わりに同じ `index.html`/`app.js` を使い回し、URLクエリパラメータ `?popout=1` の有無でCSSクラス(`body.popout-mode`)を切り替え、ツールバー・サイドバー・アウトラインパネルを非表示にするだけの分岐にした。`boot()` 関数内で早期リターンする専用の初期化パスを設け、フォルダツリーの取得や前回フォルダの自動復元(§8)など、ポップアウトでは使わない処理は最初から実行しない。

### 10.3 同期チャネルはBroadcastChannel、方向はメイン→ポップアウトの一方向のみ

`localStorage` の `storage` イベントと `BroadcastChannel` を比較し、後者を採用した。理由: `storage` イベントは値を実際に書き込んだ`document`自身では発火しない(他タブ向けの仕組み)ため意味的には使えなくはないが、本来一時的な通知に過ぎないものを永続ストレージに書き続けることになり、キーの命名・クリーンアップなど余計な設計が要る。`BroadcastChannel` は同一オリジンのタブ/ウィンドウ間のメッセージングに特化しており、値を永続化する必要がなく最小の実装で済む。

方向は**メイン→ポップアウトの一方向のみ**とし、ポップアウト側は「状態」を一切送らない設計にした(起動時の `hello`(現在状態の再送依頼)だけは例外。§10.6)。理由: 双方向にすると「メインの変更がポップアウトに伝わり、ポップアウトがそれを検知してまた何か送り返す」という経路が生まれかねず、送信元の区別やシーケンス番号などループ防止機構が必要になる。この機能は「メインウィンドウで操作し、ポップアウトは見るだけ」というマルチディスプレイの利用像に対して、一方向で要件を満たせるため、双方向化のコストを払わない判断をした。ポップアウト自身の操作(マインドマップのノードクリック等)はポップアウト内で完結させ、メイン側には伝播させない。

### 10.4 初期状態の受け渡し: テーマは`localStorage`、ファイル/マインドマップ表示はURL

ポップアウトを開いた瞬間の初期状態のうち、テーマは新たな受け渡し機構を作らなかった。既存の `toggleTheme()` が既に `localStorage.setItem('mdv.theme', ...)` を行っており、ポップアウト側の起動時処理(`initTheme()`)も既に同じキーを読むため、同一オリジンの `localStorage` は自然に共有され、URLパラメータで渡す必要がなかった。一方、表示中ファイル(ハッシュ)とマインドマップ表示中かどうかは、開いた時点のメインウィンドウの状態をポップアウトの起動URLに直接埋め込んで渡した(`window.open()` に渡すURLをメイン側が組み立てる)。マインドマップ表示状態は `localStorage` 等で永続化されていない一時的なUI状態のため、URL経由の明示的な受け渡しが唯一の手段だった(ただしURLの初期値は開いた時点のもので更新されないため、ポップアウトの再読込後の再同期は §10.6 の `hello` で補う)。

### 10.5 ウィンドウの開閉検知は`window.closed`のポーリング

ポップアウトが閉じられたことをメイン側が検知する手段として、`beforeunload`/`unload` イベントをポップアウト側からメインへ知らせる案も検討したが、ブラウザ側でタブが強制終了された場合やクラッシュ時にunloadイベントが確実に発火する保証がない。同一オリジンの子ウィンドウであれば `popoutWindow.closed` プロパティを開いた側から直接参照できるため、400ms間隔の `setInterval` でポーリングする方式にした。イベント駆動でない分の遅延(最大400ms)は、UIの復帰処理(プレースホルダー表示の解除)に対して体感上問題にならない範囲と判断した。

### 10.6 フォルダ切替・ポップアウト再読込への追従(追記, 2026-10-17)

未検証だったケースの確認(TODO.md の T4)で、実装済みの同期が取りこぼす場合が2つ見つかり、修正した。

**フォルダ切替**: サーバーの `POST /api/change-dir` はWebSocketで何も通知しないため、ポップアウトの手がかりはメインからの状態通知しかない。ところが当初の通知は `path`(相対パス)だけで、切替先のフォルダにも同じ相対パス(`index.md` など)があると「パスは変わっていない」と判断され、ポップアウトは古いフォルダの内容を表示し続けた(実機で再現)。対処として、通知に `root`(サーバーのルートの絶対パス)を含め、ルートが変わったときは相対パスが同じでも読み直すようにした。ポップアウトは起動時に `/api/config` で現在のルートを控える。切替先に `.md` が無い場合も、`path: null` と新しい `root` を通知してポップアウトに「ファイルなし」を表示する。

検討した別案は、サーバーが `change-dir` のときに全WebSocketクライアントへ `root-changed` を配ること。却下した理由は2つ。(1) メインが切替先の最初のファイルを選ぶまで正しいパスが決まらないため、ポップアウトは旧パスで読み直して404を一瞬表示してから、メインの通知で新しいパスへ遷移することになる。(2) ポップアウト以外の通常タブ(現状はフォルダ切替に追従しない)まで挙動を設計し直す必要があり、今回の範囲を超える。

**ポップアウトの再読込**: ポップアウトの起動URLに載せたマインドマップ表示の初期値は更新されないため、再読込すると(メインがマインドマップ表示のままでも)通常表示に戻って食い違った(実機で再現)。対処として、ポップアウトが起動の最後に `{type: 'hello'}` を送り、メインが通常の `state` で応える往復を足した。状態の流れはメイン→ポップアウトの一方向のままで、ポップアウトが送るのは `hello` だけ、メインが送るのは `state` だけ、メインが反応するのも `hello` だけなので、§10.3 のループ防止の理屈(固定方向なら送信元の区別もシーケンス番号も要らない)は崩れない。URLのハッシュやクエリを更新し続ける方式より、状態の持ち主(メイン)に直接聞く方が単純で、URLを書き換える副作用も無いため選んだ。

**既知の限界**: メインを再読込すると、メインはポップアウトへの参照(`window.open` の戻り値)を失う。状態の同期は再開する(メインが再読込後の最初の文書表示で通知する)が、メインは「別ウィンドウで表示中」の通知ではなく通常のプレビューを表示し、ポップアウトの閉じ検知(§10.5)も止まる。トグルボタンを押し直すと同名ウィンドウ(`mdv-popout`)が再利用されて参照が戻る想定だが、実ブラウザでの確認は未実施(TODO.md の T1)。ポップアウト側から定期的に生存通知を送ってメインが存在を把握する方式なら解消できるが、今回は見送った。

## 11. ローカルサーバーへの到達経路の防御(Host / Origin の検証、読み込み・埋め込みの防止)の設計判断(追記, 2026-10-19)

### 11.1 なぜ必要か: 「ループバック限定なら外から届かない」前提が Web ページ経由で破れる

当初の脅威モデルは「`127.0.0.1` にバインドするので、ネットワークの外からは到達できない」だった。完成度の評価(2026-10-19)で、これが **Web ページ経由では成立しない**ことを、試験用サーバーへの実測で確認した。偽の `Host`(別のドメイン名)を付けた要求がそのまま受理され、`POST /api/change-dir` で任意のフォルダへルートを切り替えられ、`/raw/<任意のパス>` がそのフォルダ内の任意の種類のファイルを返した。ブラウザ上で攻撃者のドメインを `127.0.0.1` に解決させる *DNS リバインディング*では、このドメインへの要求は同一オリジン扱いになり、CORS の制約を受けずにすべての API を呼べる。ビューアーの起動中に悪意のあるページを開くと、PC 内のファイルを読み出される可能性があった(v1.4.1 以前の公開版にも存在)。悪用には条件が多く可能性は低いが、影響が大きいため修正した。

実測では、通常の他サイトからのリクエスト(CSRF)は既に防がれていた。`express.json()` は `application/json` の本文だけを解析し(`text/plain` などの「単純リクエスト」は本文が空扱いで 400)、JSON の POST はプリフライトが必要だが、サーバーは CORS の許可ヘッダーを返さないため、ブラウザが本要求を送らない。一方、WebSocket(`/ws`)のハンドシェイクは CORS の対象外で、他サイトのページから接続できる状態だった。なお、これは `fetch` / XHR の話である。他サイトのページの `<script>`・`<img>` による読み込みも CORS の対象外で、内容を読み取らせない仕組みが無かった(独立した確認で判明。§11.7)。

### 11.2 方式: Host の許可リスト + Origin と Host の一致

すべての HTTP リクエストと WebSocket のハンドシェイクを、ルーティングや静的配信の前に検査する(`server/request-guard.js`)。

1. `Host` ヘッダーのホスト名が、`localhost`・IP アドレス(リテラル)・`--allowed-host` で明示した名前(`--host` に名前を渡した場合はその名前)のどれかであること。
2. `Origin` ヘッダーがあるときは、`http://<Host>` または `https://<Host>` と完全に一致すること。`Origin` の無い要求(アドレスバー、curl)は通す。

違反は `403`(WebSocket はハンドシェイク拒否、`ws` の `verifyClient`)。サーバーのコンソールに、拒否した値ごとに1行だけ出す(同じ値の繰り返しは出さず、記録する値は100件で打ち切って作り直す)。

検討した別案と却下の理由:

- **起動ごとのランダムなトークンを URL に載せる**: 確実だが、ブックマーク・ライブリロードの再接続・ポップアウト・スタートメニューの「サンプルを開く」・他のページからのリンクのすべてに引き回す必要があり、認証機構の導入に近い。個人用ビューアーの手軽さを損なうため見送った。
- **CORS ヘッダーで制御する**: DNS リバインディングはブラウザ上で同一オリジンになるため効かない。WebSocket も対象外。
- **`Host` を `127.0.0.1:<port>` に固定する**: `localhost` でのアクセス、IPv6(`[::1]`)、ポート転送(別のポートで受ける構成)を壊す。ポートは検査しない。
- **`Origin` だけを検査する**: リバインディングでは `Origin` も攻撃者のドメインで `Host` と一致してしまい、素通りになる。検査の本体は `Host` である。

### 11.3 IP アドレスを無条件に許可してよい理由

DNS リバインディングは、攻撃者が管理するドメイン名を使わないと成立しない。ブラウザは URL に IP アドレスが書かれていればそのまま `Host` に載せ、名前の解決を経由しないため、IP アドレスでの接続は攻撃者のドメインを経由できない。これで `--host 0.0.0.0` での LAN 公開(IP アドレスでアクセス)も、追加の指定なしで動く。IP に見せかけた名前(`127.0.0.1.evil.example`、`localhost.evil.example`)は、ホスト名の形式を厳密な正規表現で判定し、IPv4 は `net.isIPv4`、IPv6 は `net.isIPv6` で確認するため通らない。`@`・空白・スラッシュを含む値や、ポートが数字でない値、`Host` の欠落も拒否する。`localhost` の末尾のドット(`localhost.`)は1つだけ許す。

### 11.4 `Origin` は URL として解析せず、文字列で完全一致させる

`new URL()` で解析すると、`http://127.0.0.1:8931@evil.example` のように、解析結果とそれを使う側の解釈がずれる余地が生まれる。`http://<Host>` / `https://<Host>` との文字列の完全一致なら、そのずれが起きない。`null`(sandbox された iframe など)や、別のオリジン、同じマシンの別ポートのサービスのページからの要求は拒否する。

### 11.5 既知の制約

- 名前でのアクセス(`http://my-pc:8931/`)は、`--allowed-host my-pc` を付けないと拒否される。拒否の応答に、この指定方法を書いてある。
- リバースプロキシの背後では、プロキシが元の `Host` を渡し(Origin と一致させるため)、その名前を `--allowed-host` で許可する必要がある。
- `--host 0.0.0.0` で LAN に公開した場合、認証が無い点は変わらない(Host / Origin の検査は、LAN 内の別の端末からの直接アクセスを防ぐものではない)。
- ブラウザを経由しないローカルのプロセスは防げない。同じ OS ユーザーなら、そもそもファイルに直接アクセスできる。
- `/raw` の配信対象を画像・動画などに限る案は、今回は見送った。Web ページ経由の到達を塞いだことで優先度が下がり、本文中の相対リンク(CSV、PDF、ZIP など)を壊すおそれもあるため。
- Origin に `https://<Host>` も許すのは、`--allowed-host` を、TLS を終端するプロキシの背後で使う場合に、ブラウザの `Origin` が `https://` になるため。`--port 80` のときだけは、同じマシンの 443 番にある攻撃者のページ(`https://localhost`)からの要求も、同じ文字列に見えて通る。ただし、80 番での起動と、その 443 番の攻撃者のページが揃うことは現実には起きないので、そのままにした(独立した確認で指摘され、直さないと決めた)。

### 11.6 テスト

このリポジトリで最初の自動テストとして、`test/` に `node:test`(依存の追加なし、`npm test`)で追加した。`request-guard.test.js` は判定関数の単体テストで、許可する値・拒否する値(ドメインの偽装、userinfo、不正なポート、`Origin: null` など)を網羅する。`server-guard.test.js` は実際にサーバーを子プロセスで起動し、偽の `Host`・他サイトの `Origin` を付けた要求が、HTTP(API・静的ファイル・`/raw`・フォルダ切替)と WebSocket の両方で拒否され、状態(サーバーのルート)が変わらないこと、通常の要求は通ることを確かめる。修正前のコード(`62b7b75`)に対して統合テスト(10件)を実行すると、偽の `Host`・他サイトの `Origin`・WebSocket の拒否を含む6件が失敗し、通常の利用・同一オリジンの POST・ライブリロードの3件は修正前後とも通ることも確認した。組み込みの抜け(判定関数は正しいのに、ルートや WebSocket に適用し忘れる)を防ぐのが統合テストの目的である。

あわせて、既存の使い方が壊れないことを固定するテストも足した。通常の Host(`localhost`・`127.0.0.1`・`[::1]`)での画面・ポップアウト(`/?popout=1`)・API・`/raw`、ライブリロード(許可された WebSocket にファイルの変更が通知される)、`--port` の指定と使用中のときの繰り上がり、`--help` である。`--port` のテストは、使用中のポートを指定すると未処理のエラーで落ちる、v1.4.1 以前からの不具合を見つけた。`ws` の `WebSocketServer` が HTTP サーバーのエラー(`listen` の `EADDRINUSE`)を再送出するのに、受け手が無かったためで、`listenWithRetry` の「使用中なら次のポートを試す」まで届いていなかった。`wss` に `'error'` の受け手を付けて直した(`e34534f`)。

### 11.7 Origin の付かない読み込みと埋め込みの防止(`Cross-Origin-Resource-Policy` と `frame-ancestors`)

T13 の独立した確認(2026-10-19)で、Host / Origin の検査では塞げない経路が見つかった(v1.4.1 以前からある)。他サイトのページが `<script src>`・`<img src>` でビューアーのファイルを読み込む要求には、ブラウザが `Origin` を付けず(`Sec-Fetch-Site: cross-site`・`Sec-Fetch-Mode: no-cors` だけ)、`Host` もビューアー自身のもの(`127.0.0.1:<port>`)のため、検査を通る。実際に、合成のフォルダに置いた `.js` の `var` の値を、他サイトのページが読み取れた(`window.DUMMY_SECRET`)。`onload` と `onerror` の違いで、ルートの下に任意のファイル(`.md` も)があるかが分かり、画像は表示され、寸法も読めた。JSON の API は、ブラウザが不透明な応答として止めるため読めず、ルートの外やフォルダの切り替えには届かない。もう1つ、どのサイトも、ビューアーを `<iframe>` に埋め込めた(`X-Frame-Options` も `frame-ancestors` も無い)。中身は読めないが、クリックジャッキングで、タスクのチェックボックス(ファイルへの書き込み)を押させられる。

直し方は、応答のヘッダーで、ブラウザに拒否させること(`server/security-headers.js`。Express の最初のミドルウェア)。

- `Cross-Origin-Resource-Policy: same-origin` — 他のオリジンからの読み込み(`<script>`・`<img>`・`<link>`・`no-cors` の fetch)への応答を、ブラウザが破棄する。内容も、ファイルの有無も観察できなくなる(存在するファイルの 200 にも、存在しないファイルの 404 にも付くので、`onload` / `onerror` の違いも出ない)。`same-site` でなく `same-origin` にしたのは、ポートまで比べるため。`same-site` だと、同じホストの別のポートで動く別のサーバーのページ(開発用サーバーなど)からの読み込みを許してしまう。
- `Content-Security-Policy: frame-ancestors 'self'` — 他のオリジンが、ビューアーを `<iframe>`・`<object>`・`<embed>` に表示できなくなる。アプリ自身は `<iframe>` を使わず、ポップアウトは `window.open` なので、自分自身(`'self'`)だけ許せばよい。`frame-ancestors` 以外のディレクティブは付けない(`default-src` などを足すと、インラインのスクリプトやスタイルを壊すため)。`X-Frame-Options` は、`frame-ancestors` に対応しない古いブラウザのためのものなので、付けない。

実装上の注意:

- ヘッダーは、Host / Origin の検査より前に付ける。検査が返す `403` にも、見つからない `404` にも、変更なしの `304` にも付くため(付かない応答があると、そこが穴になる)。
- 未定義のパスの 404 は、Express 標準(`finalhandler`)に任せず、自前のハンドラで返す。標準の 404 は `Content-Security-Policy` を `default-src 'none'` に上書きし、`frame-ancestors` が外れてしまう(`default-src` は `frame-ancestors` の代わりにならない)。これは、全種類の応答にヘッダーが付くことを確かめるテストで見つかった。応答の本文は、HTML の `Cannot GET /...` から、ほかのエラーと同じ JSON(`{"error": ...}`)に変わる。
- WebSocket のハンドシェイクの応答(`ws` が返す)には付かない。文書でも読み込みの対象でもないため。WebSocket は §11.2 の `Origin` の検査で守る。

検討したが採用しなかったもの:

- **`Sec-Fetch-Site: cross-site` で、文書の移動でない要求をサーバーで断る**: 古いブラウザは `Sec-Fetch-*` を付けず、判定が抜ける。ブラウザ自身に遮断させる CORP の方が、確実で簡単で、GET は読み取りだけなので、サーバーで断つ利点も小さい。
- **`Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`**: ウィンドウどうしの分離のためのヘッダーで、他のオリジンからの読み込みの防止という目的に合わない。
- **`/raw` の配信対象を画像などに限る**: §11.5 のとおり、見送り。

結果として変わる使い方は 1 つだけ。**他のオリジンのページの `<iframe>` の中に、ビューアーを表示できなくなる**(たとえば、Web ページを枠に埋め込む他のツールの組み込みプレビュー。実際にそうしたツールで試してはいない)。通常のブラウザのタブ、ポップアウト(`window.open`)、`localhost`・`127.0.0.1` のどちらで開く場合も、変わらない。README と FEATURES の制限事項に書いた。

確認:

1. `server-headers.test.js` が、成功(静的ファイル・ベンダー資産・API・生ファイル)、エラー(400・403・404)、Host や Origin の検査で断った 403、304 のすべてに、2 つのヘッダーが付くことを、実サーバーで確かめる。ヘッダーのミドルウェアを外すと 3 件すべてが失敗する。期待する値は、弱める変更に気づけるよう、テスト側(`test-helpers/server.js`)に直接書いた。`exe-smoke.test.js` も、ビルド済みの exe の応答にヘッダーが付くことを確かめる(`app/server/security-headers.js` が無い古い版の exe ではスキップ)。
2. 実ブラウザ(Claude のブラウザペイン)で、他のオリジン(`evil.localhost` と、同じホストの別のポート)のページから読み込みを試した。修正前は、`<script>` で `window.DUMMY_SECRET` が読め、存在するファイルは load・存在しないファイルは error と区別でき、画像は 220×72 で表示され、`fetch(no-cors)` は応答を返し、`<iframe>` にビューアーが表示された。修正後は、すべての読み込みが `ERR_BLOCKED_BY_RESPONSE.NotSameOrigin` で拒否され(存在するファイルとしないファイルを区別できない)、`window.DUMMY_SECRET` は未定義のまま、`fetch(no-cors)` は拒否され、`<iframe>` はコンソールに `Framing ... violates ... frame-ancestors 'self'` と出て空になった。同じオリジンでは、画面・KaTeX・Mermaid・画像・ベンダー資産・API・タスクのチェックボックスの書き込み・ライブリロード(WebSocket)・ポップアウト(別タブでの文書とテーマの同期、ボタンからの `window.open`)が、修正前と同じように動いた。

### 11.8 確かめたが、直さなかったこと

独立した確認で見つかった、ブラウザからは悪用できないもの。いずれも直さない。

- **`Host` が 2 つあると、Node は最初の値を使う**: ブラウザは `Host` を 2 つ送れない。最後の値を使うプロキシの背後に置くと解釈がずれるが、そのプロキシが攻撃者の `Host` を通すことが前提になる。
- **絶対形式の要求先(`GET http://evil.example/ HTTP/1.1` に `Host: 127.0.0.1`)は、`Host` で判定する**: RFC 9112 では要求先を使う決まりだが、ブラウザが元のサーバーにこの形を直接送ることはなく、プロキシは要求先の名前を `Host` にして転送する(その名前で断る)。
- **古い WebSocket のプロトコル(version 8)は、`Origin` でなく `Sec-WebSocket-Origin` を使う**: ガードは `Origin` だけを見るので、`Sec-WebSocket-Origin` だけの握手は通る。今のブラウザは version 13 で `Origin` を付けるので、他サイトのページは、この握手を作れない。

## 12. 依存パッケージの更新と `npm audit` の読み方の設計判断(追記, 2026-10-19)

### 12.1 `npm audit` の件数は、実際に動くコードの安全とは一致しない

`npm audit` は、`package-lock.json` が指す `node_modules` のパッケージの版を数える。ところが、ブラウザで動くのは `node_modules` のパッケージではなく、束ね直した実ファイルで、配布物(ポータブル版・インストーラー)に入るのもそのファイルだけである(§6.2、§9.7)。

- `mermaid.min.js` は DOMPurify を同梱する(Mermaid 11.17.2 の束では 3.4.12)。`node_modules/dompurify`(同じ時点で 3.4.17)とは別物で、ポータブル版は後者を含めない。`npm audit` の dompurify の指摘は、動いているコードの指摘ではない。
- `markmap-lib` のブラウザ用の束(`dist/browser/index.iife.js`)は markdown-it を同梱する。`markmap-lib` は 0.18.12 が最新で、束の中の版は更新できない。
- サーバーで実行されるのは `node_modules` の版(`express` と、その依存の `qs`・`proxy-addr` ほか)である。

### 12.2 更新のあとの確認(T14 で行った方法)

1. 束ねファイルの中の版を、実ファイルで確かめる(`mermaid.min.js` の DOMPurify の版、`index.iife.js` のハッシュ)。
2. 助言が対象にする機能を、このアプリが使っているかを確かめる。Mermaid の `sanitize` の呼び出しは `ADD_TAGS`・`ADD_ATTR`・`HTML_INTEGRATION_POINTS` だけを渡し(Mermaid の `dompurifyConfig`〈アプリは設定しない。図の中の init 指示で `ADD_ATTR` を指定しても `on*` 属性が残らないことを、確認役が確かめた〉を除く)、DOMPurify の `IN_PLACE`・`CUSTOM_ELEMENT_HANDLING` の助言の対象外。`markmap-lib` は `new MarkdownIt({ html: true, breaks: true })` で使い、linkify は無効(markdown-it の助言の対象外)。`rehype-katex` は `trust` を指定しない(katex の助言は `trust` の制限の迂回)。
3. 同じ文書の描画を、更新の前後で比べる。サーバーの描画結果(`/api/doc` など)はバイト単位で、ブラウザの描画は DOM を正規化した署名(要素数、SHA-256、色の計算値、図の寸法)で。更新前は、更新前の依存を入れたクローンから、読み取り専用で起動する。Mermaid の `gitGraph` は、コミット ID が描画のたびの乱数で、同じ版でも寸法が数 px 変わるため、差としない。SVG 全体のハッシュも、class・ER・gitGraph・sankey の4種類は、同じ版・同じ実行の中でも描画のたびに変わるので、比較に使えない(要素数・文字・色・寸法で比べる)。Browser pane が非表示だと寸法が 0 になるので、寸法は、ペインを表示した状態で比べる(寸法を除いた署名の比較は、非表示でもできる)。

### 12.3 残した指摘と、見送った更新

- 残る低7件(`katex`・`mermaid`・`markmap-lib`・`remark-math`・`rehype-katex` など)は、`katex` 0.19(破壊的)・`mermaid` 12(メジャー)・旧版への巻き戻しでしか直せない。更新の必要が出たら、`rehype-katex` 7 と `markmap-lib` との整合を確かめてから行う。
- 重大の `proxy-addr`(信頼するプロキシを設定したときのみ)と高の `undici`(HTTP クライアントとして使ったときのみ。`markmap-lib` → `cheerio` 経由)は、このアプリでは該当する使い方をしていない。互換の更新で解消したが、件数が減る以外の効果は見込まない。
- Mermaid 11.17.2 でブロック図(`block-beta`)の余白が変わった(ブロックどうしの間が空く)。表示内容は同じなので許容した。
