| 位置づけ | 閲覧専用が基本。元ファイルへの書き込みは「タスクのチェックボックス切替」と「装飾ショートカット(`Ctrl+Shift+X` 打ち消し線 / `Ctrl+Shift+U` 下線)」の2経路のみ。汎用エディタにはしない | FEATURES §2.9–2.10, §8 |
| 書き込みの信頼モデル | クライアントは「どこ(範囲)」と「期待する原文」だけを送り、書き込む内容は常にサーバーが決める。書き込み前に対象位置の原文を再検証し、不一致なら書かずに拒否する。CRLF ファイルで位置がずれる不具合は修正済み | DESIGN §9.4, §9.5 / `server/write.js` |
| Markdownパーサ | unified / remark / rehype を維持。移行は不要と判断。今後移行が必要になったら事前にオーナーの許可を取る | DESIGN §9.1 |
| マインドマップ | 現在の文書の「俯瞰モード」。markmap-lib / markmap-view / d3 を同梱配信(CDN 不使用)。ノードの直接編集は見送り、代わりに「ノードをクリック→プレビューの該当箇所へジャンプ」。ノード内のリンクも既定の遷移はさせず、他のノードと同様にジャンプする | DESIGN §9.2, §9.6 / `a82a3a4` |
| ポップアウト | md-viewer にはエディタ画面がなく「エディタのテキスト変更の同期」は成立しないため、同期対象は「表示中ファイル・テーマ・マインドマップ表示」のみ。ファイル内容は各ウィンドウが持つ既存の WebSocket ライブリロードで独立に反映される。通信は BroadcastChannel で、状態は常にメイン→ポップアウトの一方向。別ビルドにせず `?popout=1` で同一バンドルをレイアウト分岐。開閉検知は `window.closed` の 400ms ポーリング | DESIGN §10 / FEATURES §2.11 |
| ポップアウトの再同期 | 状態通知にルートフォルダ(`root`)を含め、ルートが変わったときは相対パスが同じでも読み直す。ポップアウトは起動時(再読込を含む)に `hello`(現在状態の再送依頼)を送り、メインが `state` で応える。ポップアウトが送るのは `hello` だけ、メインが反応するのも `hello` だけで、一方向の性質は保つ | DESIGN §10.6 / `1fbc651` |
| テーマ適用 | トグル操作と同期受信で共通の `applyTheme()` を使う(クラス切替 + 本文の再描画。Mermaid がテーマを SVG に焼き込むため)。同期メッセージの `theme` は `light` / `dark` のみ受理する | `4e1ad2b` |
| サーバーへの到達経路の防御 | すべての HTTP と WebSocket で、Host(localhost・IP アドレス・`--allowed-host` の名前のみ)と Origin(Host と一致のみ)を検査し、違反は 403。ランダムなトークンや CORS 制御は採用しない(却下理由は DESIGN §11.2)。Origin の付かない `<script>`・`<img>` による読み込みと `<iframe>` への埋め込みは、すべての応答に `Cross-Origin-Resource-Policy: same-origin` と `Content-Security-Policy: frame-ancestors 'self'` を付けて、ブラウザに拒否させる(2026-10-19 に統括が決定。`Sec-Fetch-Site` でサーバーが断る方法は不採用。DESIGN §11.7)。Origin の `https://<Host>` は、TLS のプロキシの背後で `--allowed-host` を使う場合のために残す(DESIGN §11.5) | DESIGN §11 / `05839af` `80b92fd` |
| 配布 | 未署名の個人配布(portable zip + ユーザー単位インストーラー、管理者権限不要)。SmartScreen の警告は README に明記済み | DESIGN §6 |
| バージョン | `package.json` の `version` が唯一の情報源(起動バナーもここから読む)。リリースごとに package.json・package-lock.json・`docs/FEATURES.md` と `docs/FEATURES.ja.md` の Version 行を揃える | v1.4.1 で是正 |
| ビルド時の未コミット確認 | 配布物に入るファイルが未コミット/未追跡なら警告する。ただし処理は止めない(手元の試験ビルドを許容)。中断やコミット済みファイルのみのコピーへの厳格化はオーナー判断 | `a71bc6f` |

### 5.3 設計上の懸念(率直な指摘)

1. 【解消】テーマ適用処理が2箇所に重複して片方だけ再描画が抜けた問題は、`applyTheme()` への一本化で解消した(`4e1ad2b`)
2. `public/app.js` が約1330行の単一モジュールに肥大している(描画・検索・マインドマップ・ポップアウト同期・書き込み UI が同居)。次に機能を足す前に、テーマ・同期・マインドマップなどの分割を検討する
3. 自動テストは Host / Origin の検査(T13)にしか無い。元ファイルを書き換える経路に回帰テストが無いのが最大のリスクで、CRLF バグも手動検証で偶然見つかった(T8)。今回のポップアウトの不具合(Mermaid・フォルダ切替・再読込)も、すべて実機で再現するまで気づけなかった
4. バージョン表記の手動同期(`package.json` / FEATURES の Version 行 / インストーラーの `/DAppVersion`)でドリフトが実際に発生した(起動バナー `v1.0.0` 固定、v1.4.1 時点で FEATURES が 1.4.0 のまま)。§7.2 をチェックリストとして守るか、スクリプト化する
5. ビルドが作業ツリーの未追跡ファイルまで配布物に含める問題は、警告の追加(`a71bc6f`)で気づけるようにした。警告は見落とせるため、中断またはコミット済みファイルのみのコピーに厳格化するかは T9 で判断する
6. ポップアウトを前面に出す手段が無い。再押下は「閉じる」動作で、`openPopout()` 内の `focus()` 分岐はデッドコード。2枚目のモニタで他ウィンドウの背面に隠れると取り戻せないため、プレースホルダーに「前面に出す」ボタンを足して `focus()` を活用する案(§6)
7. ポップアウトのリモート状態適用(`applyRemoteState`)は直列化されていない。テーマ変更の再描画(非同期)中に次のファイル切替メッセージが届くと、古い描画のスクロール復元が新しい文書に適用されうる(短時間に連続操作した場合のみ。メインのテーマ切替直後にファイルを切り替えるケースと同種で、実害は小さい)
8. 状態通知が描画完了の後ろに置かれている。`setMindmapMode` / `toggleTheme` / `loadDoc` は、描画の `await` の後に `broadcastState()` を呼ぶ。マインドマップの `setData` は d3 の遷移(`requestAnimationFrame`)の完了を待つため、メインのウィンドウが非表示・完全に覆われていると遷移が進まず、通知が止まる(非表示の Browser pane で再現。実ブラウザでも完全に隠れたウィンドウなら起こりうる)。通知を状態の確定直後(描画の前)に送れば、描画の進行に依存しなくなる
9. メインがポップアウトの存在を `window.open` の戻り値でしか把握していない。メインを再読込すると参照が失われ、プレースホルダーと閉じ検知が止まる(§3.2 の T4 結果)。ポップアウトからの定期的な生存通知(ハートビート)に切り替えれば、再読込後もプレースホルダーを維持でき、`window.closed` のポーリングへの依存も減らせる
10. 【解消】サーバーが接続元の `Host` / `Origin` を検証していなかった(2026-10-19 に試験用サーバーで実測。v1.4.1 以前の公開版にも存在した。`05839af` で修正、設計は DESIGN §11)。偽の `Host`(別のドメイン名)を付けたリクエストも受理され、`POST /api/change-dir` が任意の絶対パスのフォルダへルートを切り替え、`/raw` がそのフォルダ内の任意の種類のファイルを返す。ブラウザの通常の CSRF は、JSON 以外を読まないこと・CORS 許可を返さないことで防がれているが、DNS リバインディング(攻撃者のドメインが 127.0.0.1 に解決される)ではブラウザ上は同一オリジンになるため、悪意のある Web ページが PC 内のファイルを読める可能性がある。README / FEATURES の脅威モデルは「127.0.0.1 限定なら外部から到達できない」前提で、Web ページ経由の到達を想定していない。対処(T13、実施済み): すべての HTTP リクエストと WebSocket 接続で、Host(localhost・IP リテラル・`--allowed-host` の名前のみ)と Origin(Host と一致のみ)を検査する。`/raw` の配信種別の制限は見送った(DESIGN §11.5)。`--host 0.0.0.0` で LAN に公開した場合は認証なしで読み書きされるため、起動時の警告で明示する案もある。【追記】T13 の独立検証で、Origin の付かない `<script>`・`<img>` による読み込みと `<iframe>` への埋め込みが残っていることが分かり、応答ヘッダーで塞いだ(T13-2、`80b92fd`、DESIGN §11.7)
11. 【対処済み。低7件が残る】依存パッケージの既知の脆弱性。2026-10-19 の `npm audit --omit=dev` は 12件(重大1・高1・中4・低6)だった。T14(`89b3d42`)で、互換の範囲の更新(`npm audit fix`、`--force` なし)を適用し、7件(すべて低)になった。残る7件(`katex`・`mermaid`・`markmap-lib`・`remark-math`・`rehype-katex` など。katex の「`trust` の制限を迂回できる」件に由来し、このアプリは `trust` を指定しない)は、直すには `katex` 0.19・`mermaid` 12・旧版への巻き戻しといった破壊的な変更が要るため見送り。**`npm audit` の件数は、実際に動くコードの安全とは一致しない**(DESIGN §12): ブラウザが読むのは束ね直した実ファイルで、`mermaid.min.js` は DOMPurify(3.4.12)を、`markmap-lib` のブラウザ用の束は markdown-it を同梱する。前者は `npm audit` の範囲(≤3.4.15)に残るが、その助言3件の設定(`IN_PLACE`・`CUSTOM_ELEMENT_HANDLING`)を Mermaid は渡さない。後者の助言(`linkify: true`)は、`markmap-lib` が linkify を使わないので起きない。実行時に効いた更新は Mermaid 11.17.2(Mermaid 自体の助言5件〈11.16.1 未満〉を解消)。重大の `proxy-addr`(Express 経由。信頼するプロキシを設定したときのみ)と高の `undici`(`markmap-lib` → `cheerio` 経由。HTTP クライアントとして使ったときのみ)は、このアプリでは該当する使い方をしておらず、件数が減る以外の効果は見込まない。今後も、`npm audit` の件数だけでなく、束ねファイルの版と、助言の対象の機能を使っているかを見る
12. エラーハンドラ(`server/index.js` の末尾)が `err.status` を見ず、一律 500 を返す。`express.json()` の解析エラー(不正な JSON は 400、10KB を超える本文は 413 のはず)も 500 になり、コンソールに `[server]` のエラーが出る(2026-10-19 に実測。T13-2 のときに気づいた)。要求は拒否されるので実害は小さいが、クライアントのエラー表示と運用ログを紛らわしくする。`res.status(err.status ?? err.statusCode ?? 500)` にすれば直る(小さな変更。未着手)
13. `/vendor/<フォルダ>`(末尾の `/` が無い。例: `/vendor/katex`)は、`serve-static` の 301 で `Content-Security-Policy` が `default-src 'none'` に上書きされ、`frame-ancestors` が外れる(CORP は付く)。301 の本文は表示されず、転送先(`/vendor/katex/` の 404)にはヘッダーが付くので、埋め込みは止まり、害は無い。`public/` にサブフォルダが無いので、ほかに 301 は出ない。直すなら `express.static(…, { redirect: false })`(T13-2 の再確認の情報5。v1.4.2 では直さない)
14. WebSocket のハンドシェイクの応答(101・403。`ws` が返す)と、Node が返す 400(HTTP/1.1 で Host が無いなど)には、2 つのヘッダーが付かない。どれも文書でも読み込みの対象でもないので、害は無い(WebSocket は DESIGN §11.7 に書いてある)。FEATURES(英・日)・DESIGN の「すべての応答に付く」は、この例外と上の 13 を除く HTTP の応答の意味(再確認の情報6。v1.4.2 では直さない)
15. 範囲外の Range(416 のはず)と If-Match の不一致(412 のはず)も 500 になる(上の 12 と同じ原因。ヘッダーは付く)。OPTIONS は、Express の自動の応答から、自前の 404 に変わった(アプリは OPTIONS を使わない)(再確認の「参考」。v1.4.2 では直さない)
16. ポータブル版の `node_modules` の除外が、手で書く除外リスト(`build/build-portable.mjs` の `EXCLUDE_DIRS`)で、依存が増えるたびに漏れが出る。T14 の更新で `mermaid` 11.17.2 が `fastdom`・`strictdom` を足したが、リストに無く、そのまま配布物に入った(+16 ファイル、166KB。`npm ls` で、`mermaid` からしか参照されないことを確認した。`mermaid.min.js` を配るだけの実行時には使われない)。`qs`・`undici` など、除外しない依存も、`test\`・`docs\`・`.github\` などの開発用のファイルごと入る。害は無く、大きさに占める割合も小さい(zip で約 45MB のうち +47KB)ので、v1.4.2 では直さない。直すなら、除外リストに足すのでなく、許可リスト方式(サーバーが実行時に読むパッケージだけを、`npm ls --omit=dev` の依存の到達性から決める)にする案がある。除外リストへ `fastdom`・`strictdom` を足すだけなら、1 行(99_EXE化 の rc5 の報告 §6-4 も参照。T20。確認役 補助E の情報5)

### 7.3 検証時の落とし穴

- Browser pane の `window.open` は別ウィンドウにならず同一タブを遷移させる。ポップアウトの同期検証は `tabs_create` で2タブを作り、片方を `/?popout=1#/index.md` にして行う(open / close の挙動は実ブラウザで)
- コードを変更したら、開いている全タブを読み直す。修正前のコードのまま残ったタブは、新しい通信(`hello` など)に応答せず、結果が紛らわしくなる
- Browser pane が非表示(`tabs_context` が "currently hidden" と報告)だと、`innerHeight` が 0 でスクロール・サイズ系の値が無意味になる。`requestAnimationFrame` が止まるため d3 の遷移が進まず、マインドマップの2回目以降の切替(`setData` 経由)は完了待ちで止まり、メインからの状態通知も遅れる(新規読込後の初回切替は `Markmap.create` で止まらない。§5.3-8)。ライブリロード直後に旧ノードが1つ残って見えた件も、同じ原因と推測しており、実ブラウザでの確認を T1 の項目 8 に入れた。`preview_start` 直後の最初の `navigate` が "denied or failed" になることがあるが、再試行すれば通る
- 「フォルダを開く」は `window.prompt` でパスを尋ねるため、検証では `window.prompt = () => '<絶対パス>'` とスタブしてから `#mdv-open-folder-btn` をクリックする(ダイアログでペインが固まるのを避ける)。検証後は `localStorage` の `mdv.lastRoot` と `mdv.theme` を消す(次回起動時の前回フォルダの自動復元に影響するため)
- `javascript_tool` はトップレベル `await` が使えない。`read_page` の `filter:"all"` は `display:none` の要素も列挙するため、表示状態は `getComputedStyle` で確認する
- `navigate` でハッシュだけ変えてもページは再読込されず状態が残る(SPA)。クリーンな状態が必要なら query を変えて再読込させる(コンソールログのバッファは再読込をまたいで残るため、古いエラーが見えることがある。`read_network_requests` で確認する)
- スクリーンショットが30秒でタイムアウトすることがある(PROCESS.md にも同様の記録)。DOM 検証で代替する
- Browser pane が非表示だと、`getBoundingClientRect` が 0 を返し、Mermaid の図・マインドマップの寸法の比較が無意味になる(T14・T19 で発生。セッションがどのウィンドウにも開かれていないと、`show_pane` でも表示できない)。寸法を除いた署名(要素数・文字・色)で比べるか、ペインを表示した状態で行う。実際のホイール操作も、非表示のペインでは反応しないことがあった(合成の `WheelEvent` は動く)。d3-zoom のドラッグは、合成のマウスイベントに `view: window` が無いと動かないので、実際のマウス操作(`left_click_drag`)で確かめる。Mermaid の SVG 全体のハッシュは、class・ER・gitGraph・sankey が描画のたびに変わる(乱数の ID)ので、比較に使えない(DESIGN §12.2)
- ビルドは `package.json` の version を使い、`dist/md-viewer-portable-win-x64-vX.Y.Z.zip` を上書きする。公開済みと同じ版番号のまま試験ビルドすると、手元の成果物が公開済みと食い違う。試験ビルドは `dist/portable` とそのzipを退避してから行い、終わったら戻す(チェックサムで確認)
- Windows ではカレントディレクトリにしているフォルダは削除・改名できない(`Device or resource busy`)。持続する PowerShell / Bash セッションが `dist/portable` などにいないか確認する
- Git Bash でバックグラウンド起動した exe の標準出力ログは数秒遅れて書かれる(`sleep` してから読む)。PowerShell の `Start-Process -RedirectStandardOutput` は直後に `Stop-Process` すると空になる
- 自動モードの安全判定が「claude-sonnet-5 is temporarily unavailable」で Bash / Browser 系ツールを断続的に拒否することがある(コードの問題ではない)。読み取り系の作業を挟みながら再試行する
- Git の改行は `core.autocrlf=true`(Windows)。コミット時の「LF will be replaced by CRLF」警告は無害
- インストーラーの検証は、配布用の `installer/setup.iss` のまま実行しない。この PC には MD Viewer が実際にインストール済み(`%LOCALAPPDATA%\Programs\MDViewer`、スタートメニューの「MD Viewer」グループ)で、AppId・グループ名が同じだと `/DIR` を変えてもショートカットと登録を上書き・削除するおそれがある。AppId・AppName・DefaultGroupName を変えた試験用コピーをコンパイルして検証する(2026-10-19 に 99_EXE化 へ依頼した手順)。なお、この PC のインストール済みの版は「アプリと機能」に登録が無い。installer は通常どおり登録を作って消すことを T15 で確認したため、installer の欠陥ではなく、そのインストールの経緯の側と考えられる(経緯は未確認)。さらに `desktopicon` タスクには `unchecked` が付いておらず、サイレントインストールの既定でデスクトップに「MD Viewer」ができるため、同名のまま試験すると実際のショートカットを上書き・削除するおそれがある。試験用コピーではアイコン名も変え、`/TASKS=` を付ける
- 候補版・試験ビルドは、`git clone` した別フォルダ(`C:\Build\md-viewer`)で行うと、公開済み v1.4.1 の `dist/` を上書きせず、作業ツリーとも干渉しない。版表記は、クローン側だけ `1.4.2-rc1` のようにして区別する
- Git Bash から `&` で起動した `mdv.exe`(SEA)は、`kill $!` では終了しないことがある(`node` を直接起動した場合は終了した)。PowerShell で `Get-NetTCPConnection -LocalPort <port>` からプロセスを特定し、パスを確認してから `Stop-Process` する。残すと配布フォルダがロックされ、削除できなくなる
- 新しい場所に置いた `mdv.exe`(約91MB)の最初の起動は、ウイルス対策ソフトの走査で数秒〜6秒以上かかることがある(T15)。検証スクリプトは、起動を待ってから要求を出す(0.5秒間隔のリトライなど)
