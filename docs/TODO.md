T4 の結果(Browser pane の2タブ構成。フォルダ切替は `window.prompt` をスタブして「フォルダを開く」ボタンを押して検証):

- 単一ファイルモード(`md-viewer-single`、`sample/math.md`): 問題なし。ポップアウトが描画され(KaTeX 10要素)、WebSocket に接続し、テーマ・マインドマップ切替に追従する
- フォルダ切替: **不具合あり→修正**。修正前、同じ相対パス(`index.md`)を持つ別フォルダへ切り替えると、ポップアウトが古い内容(「MD Viewer サンプル」)のまま。原因は、サーバーの `change-dir` が WebSocket で通知せず、メインの状態通知も相対パスだけだったこと。修正後は sample⇄別フォルダ(両方向)、`.md` の無いフォルダ(ポップアウトにも「ファイルなし」)、元のフォルダへの復帰のすべてで追従
- メイン再読込: ポップアウトは壊れず、メインが再読込後の最初の文書表示で通知するため同期が再開する。ただしメインは再読込でポップアウトへの参照を失い、通知(プレースホルダー)と閉じ検知が止まる。これは設計上の限界で、§5.3-9 に記録した
- ポップアウトの再読込(依頼外だが同じ領域で発見): **不具合あり→修正**。修正前、再読込するとマインドマップ表示が URL の初期値(通常表示)に戻り、メインと食い違った。修正後は `hello` の往復で復元(フォルダモード・単一ファイルモードの両方。往復は `hello` 1回と `state` 1回のみでループなし)

### 5.3 設計上の懸念(率直な指摘)

1. 【解消】テーマ適用処理が2箇所に重複して片方だけ再描画が抜けた問題は、`applyTheme()` への一本化で解消した(`4e1ad2b`)
2. `public/app.js` が約1330行の単一モジュールに肥大している(描画・検索・マインドマップ・ポップアウト同期・書き込み UI が同居)。次に機能を足す前に、テーマ・同期・マインドマップなどの分割を検討する
3. 自動テストは Host / Origin の検査(T13)にしか無い。元ファイルを書き換える経路に回帰テストが無いのが最大のリスクで、CRLF バグも手動検証で偶然見つかった(T8)。今回のポップアウトの不具合(Mermaid・フォルダ切替・再読込)も、すべて実機で再現するまで気づけなかった
4. バージョン表記の手動同期(`package.json` / FEATURES の Version 行 / インストーラーの `/DAppVersion`)でドリフトが実際に発生した(起動バナー `v1.0.0` 固定、v1.4.1 時点で FEATURES が 1.4.0 のまま)。§7.2 をチェックリストとして守るか、スクリプト化する
5. ビルドが作業ツリーの未追跡ファイルまで配布物に含める問題は、警告の追加(`a71bc6f`)で気づけるようにした。警告は見落とせるため、中断またはコミット済みファイルのみのコピーに厳格化するかは T9 で判断する
6. ポップアウトを前面に出す手段が無い。再押下は「閉じる」動作で、`openPopout()` 内の `focus()` 分岐はデッドコード。2枚目のモニタで他ウィンドウの背面に隠れると取り戻せないため、プレースホルダーに「前面に出す」ボタンを足して `focus()` を活用する案(§6)
7. ポップアウトのリモート状態適用(`applyRemoteState`)は直列化されていない。テーマ変更の再描画(非同期)中に次のファイル切替メッセージが届くと、古い描画のスクロール復元が新しい文書に適用されうる(短時間に連続操作した場合のみ。メインのテーマ切替直後にファイルを切り替えるケースと同種で、実害は小さい)
8. 状態通知が描画完了の後ろに置かれている。`setMindmapMode` / `toggleTheme` / `loadDoc` は、描画の `await` の後に `broadcastState()` を呼ぶ。マインドマップの `setData` は d3 の遷移(`requestAnimationFrame`)の完了を待つため、メインのウィンドウが非表示・完全に覆われていると遷移が進まず、通知が止まる(非表示の Browser pane で再現。実ブラウザでも完全に隠れたウィンドウなら起こりうる)。通知を状態の確定直後(描画の前)に送れば、描画の進行に依存しなくなる
9. メインがポップアウトの存在を `window.open` の戻り値でしか把握していない。メインを再読込すると参照が失われ、プレースホルダーと閉じ検知が止まる(§3.2 の T4 結果)。ポップアウトからの定期的な生存通知(ハートビート)に切り替えれば、再読込後もプレースホルダーを維持でき、`window.closed` のポーリングへの依存も減らせる
10. 【解消】サーバーが接続元の `Host` / `Origin` を検証していなかった(2026-10-19 に試験用サーバーで実測。v1.4.1 以前の公開版にも存在した。`05839af` で修正、設計は DESIGN §11)。偽の `Host`(別のドメイン名)を付けたリクエストも受理され、`POST /api/change-dir` が任意の絶対パスのフォルダへルートを切り替え、`/raw` がそのフォルダ内の任意の種類のファイルを返す。ブラウザの通常の CSRF は、JSON 以外を読まないこと・CORS 許可を返さないことで防がれているが、DNS リバインディング(攻撃者のドメインが 127.0.0.1 に解決される)ではブラウザ上は同一オリジンになるため、悪意のある Web ページが PC 内のファイルを読める可能性がある。README / FEATURES の脅威モデルは「127.0.0.1 限定なら外部から到達できない」前提で、Web ページ経由の到達を想定していない。対処(T13、実施済み): すべての HTTP リクエストと WebSocket 接続で、Host(localhost・IP リテラル・`--allowed-host` の名前のみ)と Origin(Host と一致のみ)を検査する。`/raw` の配信種別の制限は見送った(DESIGN §11.5)。`--host 0.0.0.0` で LAN に公開した場合は認証なしで読み書きされるため、起動時の警告で明示する案もある
11. 依存パッケージの既知の脆弱性。`npm audit --omit=dev` で12件(重大1・高1・中4・低6、2026-10-19)。重大の `proxy-addr`(Express 経由。信頼するプロキシを設定したときのみ)と高の `undici`(`markmap-lib` → `cheerio` 経由。HTTP クライアントとして使ったときのみ)は、このアプリでは該当する使い方をしておらず、実害は見込まない。実質的に注意が要るのは、中の `mermaid`・`dompurify`(他人の図や HTML を描画するとき)と `markdown-it`(巨大な文書で処理が止まる)。重大・高・中の6件は `npm audit fix` で解消できると表示される(互換性のある更新)。低の6件(`katex` 系)は破壊的変更でしか解消できず見送り。対処(T14): 更新後に Mermaid・数式・マインドマップ・コードの色付けの描画を回帰確認する

**指示1の要点との対応**

| 指示1の要点 | 対応 | 確認 |
| --- | --- | --- |
| Host が、この PC の名前(localhost・127.0.0.1・[::1])でない要求は断る | `localhost`・IP アドレス(IPv4、角括弧つきの IPv6)・`--allowed-host` の名前だけ許可し、ほかは 403。**ポートは検査しない**(下記の注) | 単体テスト(許可する値・拒否する値)、統合テスト(偽の Host で API・静的ファイル・`/raw`・フォルダ切替が 403)、実ブラウザ(`evil.localhost`) |
| Origin が付いていて、自分自身でない要求は断る | Origin があるとき、`http(s)://<Host>` と完全一致しなければ 403。HTTP と WebSocket の両方。Origin が無い要求(アドレスバー、curl)は通す | 統合テスト(他サイトの Origin、`null`、別ポートのページの Origin で POST と WebSocket が 403)、実ブラウザ(他オリジンの WebSocket・fetch) |
| 断るときの応答と、利用者が困ったときの説明(README・ヘルプ) | 403 と、理由と `--allowed-host` の案内を書いた JSON。サーバーのコンソールに値ごとに1行。README(英・日)・FEATURES(英・日)・`mdv --help` に記載 | 統合テスト(応答の文面)、`--help` のテスト |
| 既存の使い方(ブラウザで開く・ポップアウト・`--port` の指定・exe 版)が壊れないことを、自動テストで固定する | 下記の「テストの結果」のとおり | `npm test` |

注(ポートを検査しない理由): DNS リバインディングは、URL のポートに接続するため、Host のポートは常にこのサーバーのポートと一致する。ポートを検査しても防御は強まらず、ポート転送(SSH の `-L` など)を壊すだけなので、検査しないことにした。別ポートのページからの要求は、Origin(ポートを含む)の不一致で拒否される。同じ理由で、IP アドレスは(この PC のものかを調べず)すべて許可している(DESIGN §11.3)。指示1の文面どおりにポートや IP を厳格にする必要があれば、指示2でお知らせください(小さな変更で足せます)。

**何を変えたか**

- `server/request-guard.js`(新規): Host / Origin の判定。`server/index.js`: 全リクエストの最初のミドルウェアと、WebSocket の `verifyClient` に組み込み。`bin/mdv.js`: `--allowed-host NAME`(複数指定可。名前で指定した `--host` も許可)を追加
- ポートが使用中のとき、自動で +1 に繰り上がらず、未処理のエラーで落ちる不具合(v1.4.1 以前の公開版の exe でも再現)を、テストで見つけて修正(`e34534f`)。原因は、`ws` が HTTP サーバーのエラーを `WebSocketServer` から再送出するのに、受け手が無かったこと
- 設計は DESIGN §11、仕様は FEATURES §3〜§5、README(英・日)
